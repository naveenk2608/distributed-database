# dkv benchmarks

Generated by `dkv-bench report` from the 87 result files in `bench/results/` (`make bench-local`
runs the matrix and regenerates this file). Every number is the median over a variant's runs,
with the lowest and highest in parentheses. Latencies are client-side, from issuing an
operation to its answer (in open loop, from its intended start), in milliseconds.

The nodes' own numbers cover the measured time: "Fsync" is persisting a Raft Ready that needs
an fsync, "Commit" a write from proposal to apply on its leader, both over every replica of
every node. "Write amp." is the bytes written to the Raft logs, the engines' own logs, flushes
and compactions per byte of keys and values applied, over every replica: about 1 plus the log
records' overhead until memtables flush. Raw data: each result file holds the run's full
configuration, the latency histogram and these counters.

## Reruns

The matrix shared the machine with an editor (VS Code, its extensions and language servers), other terminal sessions and system services. A sampler read /proc every 5 seconds throughout: every process's CPU time, the VM's total CPU and the thread count of other WSL distros. "Outside" CPU is every process that is not part of the benchmark, the sampler excluded; its median over the matrix's measured windows, 0.064 cores (1.27 CPU-s per 20 s), is the idle floor. After the matrix, with the same build and seed, a run was repeated if another WSL distro started during it (Docker Desktop's did, from 12:55 to 12:58 UTC, during three runs), or if outside processes used more than 1 CPU-s above the floor in its 20 measured seconds. Each run got at most three attempts: the first that passed is used, otherwise the one with the least outside CPU, so the choice never looks at throughput. Twelve runs did not pass in three attempts. The 4000-byte-value runs push the idle editor processes into swap on this 3.7 GiB machine, and those processes then spend CPU, mostly system time, paging back in; that flagged every attempt of those runs and, in the rerun sessions, most runs after them. The other failed attempts caught the language server's periodic work (about 2 CPU-s every two minutes) or the editor's. No run shows a gap in the sampler's 5-second heartbeat (the longest is 9 s) or a wall time more than a second longer than its preload, warm-up and measured time.
